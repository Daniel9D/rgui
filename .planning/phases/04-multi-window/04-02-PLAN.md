<objective>

Replace the `ProcessContext` stub from plan 04-01 with the full D-13 struct: a process-global `NodeIdAllocator` shared across all runtimes and an optional shared `AccessibilityBackend`. Add the `Send + Sync` bounds to `ImeHostDriver` and `AccessibilityBackend` so that `UiRuntime: Send + Sync` is a real guarantee (D-17). Document the interior-mutability pattern on the trait rustdocs (D-18). Confirm D-19's static assert compiles.

The output is a runtime where two `UiRuntime` instances in the same process can be moved to different threads, share a process-global NodeId space, optionally share a screen reader backend, and route per-window events without a host mutex.

</objective>

## Task 5: Wire `node_ids` into the existing per-frame `IdAllocator` so process-global NodeIds flow into the snapshot

**Action:**

This is the integration step. Today, every `UiRuntime::update` call creates a fresh per-frame `IdAllocator` (see `src/runtime/tree.rs:29-43` and how `FrameBuilder::new` consumes it). The `NodeId`s in the resulting `UiSnapshot` are the ids issued by that per-frame allocator. For Phase 4, the snapshot's `NodeId`s must be the process-global `NodeIdAllocator` values, so the WIN-04 test (in 04-03) can prove two runtimes have disjoint node-id ranges.

Find every `IdAllocator::fresh` call in the lib (grep for `IdAllocator` in `src/`). Replace the per-frame allocator with the process-global `NodeIdAllocator::fresh()` issued from `self.node_ids`. The new `IdAllocator` type at `src/runtime/tree.rs:29-43` becomes a thin wrapper that takes a `u64` (the globally-issued id) and exposes the same `fresh()` / `Box::leak` semantics to the `FrameBuilder`. Concretely:

- Keep the `IdAllocator` struct; add `IdAllocator::with_id(global_id: u64) -> Self` that takes a pre-issued id.
- Update `FrameBuilder` (or whichever struct currently holds the `IdAllocator`) to either accept an external `&NodeIdAllocator` or take a `Vec<u64>` of pre-issued ids.
- The simplest implementation: in `UiRuntime::update`, before constructing the `FrameBuilder`, drain `self.node_ids.fresh()` calls for each id the tree will need. The exact count is determined by the tree walk; the existing code likely already has a `let next_id = self.next_id` and `self.next_id += N` pattern. <notes>

**Why `Option<SharedAccessibility>` on `UiRuntime` (not just `SharedAccessibility`):** Mirrors the process-level opt-in. A host that explicitly does not want a screen reader can pass `ProcessContext::new_without_a11y()`, and the runtime's `a11y` field is `None`. The `a11y()` method on `UiRuntime` returns `Option<&SharedAccessibility>` so the runtime knows to skip a11y calls in the `None` case.

**Why `Arc<AtomicU64>` (not `Arc<Mutex<u64>>`):** The counter is monotonically incremented and read; `fetch_add` is lock-free. `AtomicU64` with `Ordering::Relaxed` is sufficient because the only requirement is uniqueness of issued ids (no happens-before relationship needs to cross the counter). This is the same pattern used in many lock-free id allocators (e.g. `wgpu`'s id generator).

**Why the per-frame `IdAllocator` stays (just loses its counter):** The per-frame allocator exists because the tree walk needs to know how many ids to issue upfront (to size the `Vec<NodeId>` in the `FrameBuilder`). Removing it entirely would require lazy id issuance, which is a larger refactor. The cleanest path is: `NodeIdAllocator` issues the process-global ids, the per-frame `IdAllocator` is just a `Vec<u64>` of pre-issued ids, and the tree walk consumes them in order.

**Risk:** If a downstream crate in the workspace (or in a future test) has an `impl ImeHostDriver` with a non-`Send` field, the bound change is a breaking change. The 51 integration test files are the only known implementors; Task 4's verification step (`cargo build --all-targets`) catches regressions.

**Relationship to 04-01:** The 04-01 static assert (D-19) compiles today because `UiRuntime`'s fields are all `Send + Sync` already. The static assert is a forward-looking guard. The 04-02 trait bounds make the guard *meaningful*: without the bounds, a future `impl ImeHostDriver` could violate `Send + Sync` and the assert would still pass. With the bounds, the assert is a real regression detector.

**Relationship to 04-03:** The 04-03 plan constructs two `UiRuntime` instances from a shared `ProcessContext` and a shared `SharedWgpuDevice`. This plan's `NodeIdAllocator` is what makes WIN-04 (snapshot isolation) provable: the two runtimes share one counter, but their `(window_id, node_id)` tuples are still unique.

</notes>
