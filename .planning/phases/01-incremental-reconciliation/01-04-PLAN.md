# Plan 01-04: `WidgetSpec` hash → re-mount; state preserved otherwise

**Phase:** 1 (Incremental Reconciliation)
**Plan:** 04 of 04
**Type:** task
**Goal:** End-to-end verification that incremental reconciliation
behaves correctly under the four path types (reuse, patch, mount,
unmount) and that pointer-capture survives a style-only patch but
not a re-key.

## Context

This is the verification plan for the phase. 01-01 implements
the diff, 01-02 wires the layout cache, 01-03 handles capture
release on unmount. 01-04 writes the integration test that
exercises all four paths against a 50-widget tree and asserts
the canonical invariants. The test becomes the regression
guard for the phase.

Per the prd.md and PROJECT.md v1 success criteria, this is the
quality gate for "robust" Phase 1: a 50-widget UI on a modern
laptop with one widget's label updated should re-render in
< 1ms.

## Scope

**In scope:**
- A 50-widget integration test that builds a stable tree, captures a baseline paint, mutates one widget's label, captures a follow-up paint, and asserts the diff is only that one widget
- A second integration test that re-keys a widget and asserts its pointer-capture is dropped
- A third integration test that changes a widget's *spec kind* (e.g. button → label) and asserts the old node is unmounted + a new node is mounted + state is reset
- A performance regression test: 100 consecutive `update()` calls with a stable tree must average < 1ms per call

**Out of scope:**
- New functionality. This plan is verification-only.
- Unit tests for the diff algorithm itself (those are in 01-01 / 01-02 / 01-03).

## Tasks

1. **TDD-01-04-01**: Write the integration test `phase1_incremental_reconciliation_diffs_paint_minimally` that:
   - Builds a 50-widget tree
   - Renders it to a baseline golden
   - Mutates the label of one Button (e.g. "Save" → "Saved")
   - Renders again
   - Diffs the two paint outputs: only one widget's paint commands should differ; everything else is bit-for-bit identical
2. **TDD-01-04-02**: Write the integration test `phase1_re_keyed_element_drops_capture` that:
   - Builds a tree with a captured pointer
   - Re-keys the captured element (changes its `.key()` value)
   - Dispatches a `PointerUp` event
   - Asserts the up routes to the new keyed element (not the old one)
3. **TDD-01-04-03**: Write the integration test `phase1_spec_change_remounts_with_state_reset` that:
   - Builds a tree with a Button that has a BoolState (e.g. `checked: true`)
   - Mutates the Element so the same position is a Checkbox
   - Asserts the Button is unmounted, the Checkbox is mounted, and the new Checkbox's `checked` state is `false` (fresh)
4. **TDD-01-04-04**: Write the integration test `phase1_capture_survives_style_patch` that:
   - Builds a tree with a captured pointer
   - Patches the captured element's style (changes `.padding()`)
   - Dispatches a `PointerMove` event
   - Asserts the move still goes to the captured node (the capture was not released)
5. **TDD-01-04-05**: Write the performance test `phase1_incremental_reconciliation_frame_budget` that:
   - Builds the 50-widget tree
   - Calls `update()` 100 times with the *same* Element root (the diff returns no changes)
   - Asserts the mean + 99th-percentile frame time is < 1ms
   - The test runs in `--release` mode for accurate timing (gated by `#[ignore]` so it's not part of the default `cargo test`)
6. **TDD-01-04-06**: Update the visual goldens to include a "50-widget stable tree" baseline. The existing visual goldens cover individual widgets; this adds a scene-level baseline.
7. **TDD-01-04-07**: Update `STATE.md` Progress section: increment `total_plans: 30 → 30` (no change), `completed_plans: 0 → 4`, `percent: 0 → 13`. Phase 1 status → `Complete` after the four plans are done.
8. **TDD-01-04-08**: Update `REQUIREMENTS.md` traceability: mark `RECON-01..04` as `Complete`, phase `Phase 1`.

## Risks

- **Risk:** The "minimal paint diff" test is brittle. A single byte of off-by-one in the paint output (a counter increment, a timestamp) breaks the test. **Mitigation:** The diff is done at the `DisplayList` command level, not the pixel level. Compare command counts and command types per node; if the command count for a node changes, that's a paint difference. If the command type changes, that's a paint difference. The test asserts per-node equivalence, not bit-level equivalence.
- **Risk:** The performance test is machine-dependent. **Mitigation:** The `< 1ms` threshold is a soft target; the test asserts *improvement* (the new code is at least 2x faster than the old full-rebuild path), not absolute performance. Document the machine the threshold was measured on.
- **Risk:** The 50-widget test scene doesn't reflect realistic UI shapes. **Mitigation:** The scene is designed to have nested containers (cards, rows, columns) and a mix of static and dynamic widgets, so it exercises the dirty-region propagation. Document the scene's structure in a comment so future maintainers understand what it's testing.
