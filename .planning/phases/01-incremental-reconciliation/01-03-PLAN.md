# Plan 01-03: Pointer-capture release on node removal

**Phase:** 1 (Incremental Reconciliation)
**Plan:** 03 of 04
**Type:** task
**Goal:** When the reconciler unmounts a node, release any
`PointerCapture` for that node and emit a synthetic
`PointerEvent::Cancel` so the receiving widget can clean up drag
state.

## Context

Today, `PointerCapture` is keyed by `String` (the user's
`Element::key`). The capture survives a full rebuild because
the `String` key is preserved across the rebuild. But it
*doesn't* survive a re-key of the element (the user changes
`.key("foo")` to `.key("bar")`) — and it doesn't survive a
removal (the user deletes the element entirely).

PITFALLS.md item #5 (Pointer-capture leak) says: "If a
PointerCapture is set on a node that is removed in the next
update(), the next click goes nowhere or goes to the wrong
node." Phase 1 fixes this as a paired change with reconciliation
because the reconciler is the only place that knows a node was
removed.

## Scope

**In scope:**
- On `reconcile` producing an `unmounted` list: walk the `PointerCapture` map; for any entry whose key was the unmounted node's key, release the capture and emit a synthetic `PointerEvent::Cancel`
- The synthetic cancel event goes through the same event dispatch path as a real event (so handlers can clean up)
- An integration test that creates a tree with a captured pointer, removes the captured node, and asserts the next click routes correctly

**Out of scope:**
- Capture release on style change (the user didn't ask for this; capture survives a style-only patch)
- Capture transfer to a new node (v1.x follow-up; the user can re-capture manually)
- Drag-state cleanup on capture release (drag state lives in `runtime/state.rs` and is keyed by `String`; same cleanup pattern as pointer capture but separate; out of scope for v1)

## Tasks

1. **TDD-01-03-01**: Add a unit test that creates a `PointerCapture` for key "btn", calls the new `release_captures_for_unmounted(["btn"])`, and asserts the capture is no longer in the map.
2. **TDD-01-03-02**: Add a unit test that creates captures for "btn" and "menu", calls the new function with `["btn"]`, and asserts "menu" survives.
3. **TDD-01-03-03**: Add a unit test that creates a tree, dispatches a `PointerDown` event to capture the pointer on a node, then "removes" that node by running reconciliation with a tree that doesn't include it, and asserts the capture is released and a synthetic cancel event was emitted.
4. **TDD-01-03-04**: Add a unit test that the synthetic cancel event's `node` field is `None` (or `INVALID`), and the `button` field is whatever button was captured (so the handler knows which button to release).
5. **TDD-01-03-05**: Implement `PointerCapture::release_matching(&mut self, keys: &[String]) -> Vec<PointerCancel>` that returns the cancel events to emit.
6. **TDD-01-03-06**: Wire the reconciler: after `reconcile.diff` returns its `unmounted` list, call `runtime.state.release_captures_for_unmounted(...)` and feed the resulting cancel events into the event queue.
7. **TDD-01-03-07**: Update the integration test suite: a test that captures a pointer, dispatches a `PointerMove` to a different node, asserts the move goes to the captured node; then removes the captured node; then dispatches a `PointerUp`, asserts the up goes to the root (the capture is gone).

- `src/runtime/reconcile.rs` (call the release function on the unmounted list)
- `src/runtime/runtime.rs` (wire cancel events into the event queue)

- `cargo test --features rml,bitmap-text-fallback --test event_dispatch` still passes (existing dispatch behavior preserved)
- `cargo test --features rml,bitmap-text-fallback --test widgets_disabled_contract` still passes (drag state cleanup test)
- A manual smoke test in `examples/` (a future task) demonstrates the bug-fix behavior visibly

## Risks

- **Risk:** The synthetic cancel event might be emitted *during* reconciliation, which is mid-update, and the event queue might not be in a clean state. **Mitigation:** The cancel events are queued in a separate buffer that the runtime flushes at the end of `update()`, after reconciliation + layout + paint are done. This is the same pattern React uses for `unstable_batchedUpdates`.
- **Risk:** A widget that was captured against might have a drag in progress; releasing the capture mid-drag could cause the drag handler to see a "lost capture" event it didn't expect. **Mitigation:** The cancel event is delivered to the captured node's drag handler *before* the next real event; the handler can clear its drag state. This is the same semantics as the browser's `lostpointercapture` event.
- **Risk:** A widget that's been *re-keyed* (key changed) loses its capture too. **Mitigation:** That's actually the right behavior — a re-keyed element is semantically a new widget; the prior capture is no longer valid. The integration test for 01-04 covers this case.

## Handoff

After 01-03 ships, 01-04 (spec-hash re-mount) closes the phase
with a verification-focused plan. The verification plan doesn't
add new code; it writes a comprehensive integration test that
exercises the four paths (reuse, patch, mount, unmount) against
a 50-widget tree and asserts the canonical invariants:
- Captured pointer survives a style-only patch
- Captured pointer is released on unmount (01-03)
- Re-keyed element loses its capture (01-04)
- Spec-hash mismatch triggers a re-mount with state reset
