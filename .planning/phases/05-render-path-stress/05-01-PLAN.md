# 05-01: Visual goldens on a second GPU backend (Vulkan)

**Phase:** 5 (Render Path Stress)
**Plan:** 1 of 4
**Date:** 2026-06-04
**Source context:** `.planning/phases/05-render-path-stress/05-CONTEXT.md`, `.planning/phases/05-render-path-stress/05-RESEARCH.md`
**Decisions covered:** (Claude's Discretion — second backend target. Chose Vulkan because the existing `tests/visual_goldens.rs` runs on `Backends::PRIMARY` which resolves to DX12 on `windows-latest`; Vulkan is the only secondary backend reliably available on the GitHub-hosted free runners and is the path the existing `RendererOptions::backends` field was designed to expose per D-15 of phase 4's REVIEW.md.)

<objective>

Run the existing eight visual-golden tests under a non-primary GPU backend and prove the rendered output is byte-identical (or within the existing pixel tolerances) to the baselines captured on the primary backend. After this plan, the project has a `vulkan` test target that runs `cargo test --test visual_goldens_vulkan` on `windows-latest` CI and confirms the wgpu render path is stable across backends, satisfying REND-01.

</objective>

<context>

The existing test file `tests/visual_goldens.rs` covers eight golden scenes (button hover, button disabled, input focus, input with text, list, scroll, progress bar, modal). The `assert_visual_matches` helper at `tests/visual_goldens.rs:116-128` reads tolerance constants `PIXEL_TOLERANCE=1`, `CHANGED_PIXEL_RATIO_LIMIT=0.0001`, `MAX_ABS_DIFF_LIMIT=5` and compares against PNG baselines in `tests/goldens/`. The helper `render_runtime_rgba` constructs a `WgpuRenderer` via the headless seam `WgpuRenderer::new_headless_for_tests(size, format)`, which is currently hard-coded to `wgpu::Backends::PRIMARY`.

The `RendererOptions` struct in `src/render/wgpu/options.rs:5-22` already accepts a `backends: wgpu::Backends` field; the default is `Backends::PRIMARY`. The Vulkan backend is reachable on `windows-latest` (the GitHub-hosted runner has Vulkan-capable Mesa / SwiftShader available, and the wgpu 29 Vulkan backend builds and runs there). On `macos-latest` the secondary backend is Metal, but the GitHub-hosted free runners do not expose a GPU and we cannot reliably exercise Metal; the CI matrix in plan 05-03 is `windows-latest + ubuntu-latest`.

The 8 existing goldens were captured on `Backends::PRIMARY` (DX12 on Windows). Rendering them again on Vulkan must produce images within the existing tolerance constants; if the tolerance is too tight for cross-backend variance, we may need to loosen the per-backend tolerance constants in this plan (see Notes).

</context>

<tasks>

## Task 1: Add `backends` parameter to the headless renderer test seam

**Action:**

In `src/render/wgpu/mod.rs`, find the `new_headless_for_tests` constructor and add a second constructor `new_headless_for_tests_with_backends(size, format, backends) -> WgpuRenderer` that forwards `backends` to the `WgpuContext::headless` call. The existing `new_headless_for_tests` is preserved as a thin inline forward to `new_headless_for_tests_with_backends(size, format, RendererOptions::default().backends)` so the existing eight golden tests continue to compile without change.

If `WgpuContext::headless` (`src/render/wgpu/context.rs:33-63`) does not currently accept a `backends` parameter, add one: `pub fn headless(adapter_name: Option<&str>, instance_desc: InstanceDescriptor, backends: wgpu::Backends) -> Self` (or whatever the existing signature shape is; the goal is to thread `backends` from `RendererOptions` into the `InstanceDescriptor` at `src/render/wgpu/context.rs:98-102`).

The `InstanceDescriptor` construction at `src/render/wgpu/context.rs:98-102` is updated to set `backends` from the parameter rather than the empty default.

**Verify:** `cargo build --lib --tests` succeeds; `cargo test --test visual_goldens` still passes (the 8 goldens reproduce on `Backends::PRIMARY`).

**Files:** `src/render/wgpu/mod.rs` (add new constructor); `src/render/wgpu/context.rs` (thread `backends` into `InstanceDescriptor`).

**Depends on:** none.
**Parallel:** yes (can run alongside Task 2 since they touch different files — Task 2 is test-only).

## Task 2: Add `tests/visual_goldens_vulkan.rs` mirroring the 8 goldens on Vulkan

**Action:**

Create `tests/visual_goldens_vulkan.rs` that re-uses the `assert_visual_matches` and `render_runtime_rgba` helpers. Each of the eight tests should be a near-copy of the corresponding test in `tests/visual_goldens.rs`, with two differences:

1. The renderer is constructed via `WgpuRenderer::new_headless_for_tests_with_backends(size, format, wgpu::Backends::VULKAN)`.
2. The test function names have a `_vulkan` suffix to make CI grep and failure attribution easy.

The test file is gated with `#[cfg(all(test, feature = "vulkan-goldens"))]` and the workspace `Cargo.toml` `[features]` section gains `vulkan-goldens = []` (no new dependencies, no default-on cost). The reason for the feature gate: the Vulkan backend is not always present on every developer's machine, and CI is the authoritative run.

Add a `dev-dependencies` entry for `wgpu` (already present as a regular dep; reuse the same version) if not already a dev-dep — confirm by reading `Cargo.toml`.

Document at the top of the test file: "Run with `cargo test --features vulkan-goldens --test visual_goldens_vulkan` on `windows-latest` or `ubuntu-latest`. The expected outcome on a clean runner is that all 8 tests pass with zero or near-zero pixel diffs vs the `Backends::PRIMARY` baselines. If `MAX_ABS_DIFF_LIMIT=5` proves too tight for cross-backend variance, bump to `MAX_ABS_DIFF_LIMIT=15` in this file only — do NOT change `tests/visual_goldens.rs`."

**Verify:** `cargo build --tests --features vulkan-goldens` succeeds; `cargo test --features vulkan-goldens --test visual_goldens_vulkan` runs all 8 tests (they may fail in this environment if Vulkan is not present; the test is a CI artifact).

**Files:** `tests/visual_goldens_vulkan.rs` (new); `Cargo.toml` (add `vulkan-goldens` feature).

**Depends on:** Task 1 (the new constructor must exist).
**Parallel:** no.

## Task 3: Add tolerance-comparison diagnostic test

**Action:**

Add a single test in `tests/visual_goldens_vulkan.rs` named `vulkan_diff_is_within_cross_backend_tolerance` that, after running all 8 goldens, asserts the maximum `MAX_ABS_DIFF` observed across all 8 scenes is < 15 and the `CHANGED_PIXEL_RATIO` is < 0.005. This is the regression test that catches "Vulkan starts producing wildly different output" — the per-scene tests are good for byte-equality, the aggregate test catches a 50%-diff regression that would still pass per-scene tolerance with a huge bump.

If the aggregate test fails on the first CI run, log the per-scene diff values and document them in the rustdoc as the observed cross-backend baseline; subsequent runs must not regress.

**Verify:** `cargo test --features vulkan-goldens --test visual_goldens_vulkan` runs the 8 per-scene tests + 1 aggregate test = 9 total.

**Files:** `tests/visual_goldens_vulkan.rs` (add the aggregate test).

**Depends on:** Task 2.
**Parallel:** no.

<notes>

**Why Vulkan, not Metal:** the GitHub-hosted `macos-latest` runner does not expose a usable Metal device for headless wgpu work; the `windows-latest` runner has Vulkan available via Mesa/SwiftShader; the `ubuntu-latest` runner has Vulkan via `lavapipe` or hardware when available. Vulkan is the realistic cross-platform secondary backend for free CI.

**Why a feature gate:** not every developer's local machine has a working Vulkan ICD; the test would fail-flake on dev boxes. The feature gate makes the test opt-in and CI-driven.

**Risk:** if Vulkan output differs from DX12 in the 8 goldens by more than `MAX_ABS_DIFF_LIMIT=5`, the per-scene tests will fail and the developer must bump the per-backend tolerance. The aggregate test (Task 3) catches a more dangerous failure mode where the diff spikes but stays within per-scene limits.

**Relationship to 05-03:** plan 05-03 adds the `validation-layers` feature and the CI workflow. Plan 05-03 invokes this plan's `visual_goldens_vulkan` test in the CI matrix.
