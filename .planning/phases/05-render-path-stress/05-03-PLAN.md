# 05-03: Vulkan validation layers in CI (`validation-layers` feature + CI workflow)

**Phase:** 5 (Render Path Stress)
**Plan:** 3 of 4
**Date:** 2026-06-04
**Source context:** `.planning/phases/05-render-path-stress/05-CONTEXT.md`, `.planning/phases/05-render-path-stress/05-RESEARCH.md`
**Decisions covered:** (Claude's Discretion — validation layer placement. Chose a Cargo feature gate over a runtime env var because: (1) the `RendererOptions` struct already follows the feature-gate pattern via `Cargo.toml` features; (2) env-var-based toggles conflict with deterministic test runs in CI; (3) feature gates make the `cargo test` matrix self-documenting in the CI workflow YAML.)

<objective>

Add a `validation-layers` Cargo feature that, when enabled, configures the wgpu `InstanceDescriptor` with `wgpu::InstanceFlags::VALIDATION` and adds a GitHub Actions CI workflow that runs the full test suite under that feature on `windows-latest` and `ubuntu-latest`. After this plan, the project has CI-run validation that surfaces buffer-alignment issues, push-constants mistakes, and other wgpu validation errors that the default release path silently allows. REND-03 is satisfied.

</objective>

<context>

The `WgpuContext::headless` function constructs an `InstanceDescriptor` at `src/render/wgpu/context.rs:98-102` with only `backends` set. The `wgpu::InstanceFlags` type (wgpu 29) has a `VALIDATION` variant that enables Vulkan validation layers (or the equivalent Metal/DX12 debug layer). The `InstanceDescriptor` field is `flags: InstanceFlags` and is constructed via `Default::default()` today.

Validation layers are debug-only; they impose a 2–5× render time cost and are not appropriate for production. The standard pattern in the wgpu ecosystem is to gate them behind a `cfg` flag.

The project currently has no `.github/workflows/` directory. This plan adds the first one.

The CI matrix is `windows-latest` (DX12 PRIMARY + Vulkan SECONDARY available) and `ubuntu-latest` (Vulkan via Mesa or hardware). `macos-latest` is not included because the GitHub-hosted free runners do not expose a Metal device that wgpu can drive headlessly.

</context>

**Action:**

Add the feature to the `[features]` section of `Cargo.toml`:


The feature is empty (no new dependencies). Document in a comment above the feature:

```toml
# Enable wgpu validation layers (Vulkan: VK_LAYER_KHR_validation, Metal: Metal Validation,
# DX12: D3D12 Debug Layer). Imposes a 2-5x render time cost. Used in CI to surface
# buffer-alignment, push-constants, and other validation issues that the default
# release path silently allows. Not for production builds.
validation-layers = []
```

**Verify:** `cargo build --lib` succeeds; `cargo build --lib --features validation-layers` succeeds (no compile-time change yet — the feature is read in Task 2).

**Files:** `Cargo.toml` (add feature).

**Depends on:** none.
**Parallel:** yes (independent of Tasks 2 and 3).

## Task 2: Wire the feature into `WgpuContext`

**Action:**

In `src/render/wgpu/context.rs`, find the `InstanceDescriptor` construction (around `context.rs:98-102`) and gate the `flags` field on the new feature:

```rust
let flags = if cfg!(feature = "validation-layers") {
    wgpu::InstanceFlags::VALIDATION
} else {
    wgpu::InstanceFlags::default()
};

let instance_desc = wgpu::InstanceDescriptor {
    backends,
    flags,
    ..Default::default()
};
```

Document the gating in a rustdoc comment on the `headless` function: "When the `validation-layers` Cargo feature is enabled, this function sets `wgpu::InstanceFlags::VALIDATION` on the `InstanceDescriptor`. The validation layer must be installed on the host (Vulkan: `VK_LAYER_KHR_validation` via the Vulkan SDK; Metal: built into macOS; DX12: installed with the Windows SDK)."

If the `WgpuContext` has a non-headless constructor (e.g. for winit), apply the same gating there.

**Verify:** `cargo build --lib` succeeds (no feature: flags is default); `cargo build --lib --features validation-layers` succeeds (flags is VALIDATION). `cargo test --lib --features validation-layers` runs the existing tests under validation; if any test triggers a wgpu validation error, the test fails (which is the correct outcome — surface the issue).

**Files:** `src/render/wgpu/context.rs`.

**Depends on:** Task 1.
**Parallel:** no.

## Task 3: Add `.github/workflows/ci.yml`

**Action:**

Create `.github/workflows/ci.yml` with the following jobs:

1. **`test`** — runs on `windows-latest` and `ubuntu-latest`. Steps:
   - `actions/checkout@v4`
   - `dtolnay/rust-toolchain@stable`
   - `Swatinem/rust-cache@v2` (cache `~/.cargo` and `target/`)
   - For `ubuntu-latest`, install Vulkan validation layers: `sudo apt-get install -y vulkan-validationlayers mesa-vulkan-drivers`
   - For `windows-latest`, the Vulkan SDK is not pre-installed; instead, rely on the Mesa software Vulkan ICD that ships with the runner. (If a future iteration needs `VK_LAYER_KHR_validation` on Windows, add a `hunspelljr/vulkan-validation@v1` step; defer for now.)
   - `cargo test --lib --tests` (default features; sanity)
   - `cargo test --lib --tests --features validation-layers` (validation-enabled)
   - `cargo test --lib --tests --features vulkan-goldens` (plan 05-01's test)

2. **`clippy`** — runs on `ubuntu-latest`. Steps:
   - `actions/checkout@v4`
   - `dtolnay/rust-toolchain@stable` with `components: clippy, rustfmt`
   - `Swatinem/rust-cache@v2`
   - `cargo clippy --all-targets --all-features -- -D warnings`
   - `cargo fmt --all -- --check`

3. **`doc`** — runs on `ubuntu-latest`. Steps:
   - `actions/checkout@v4`
   - `dtolnay/rust-toolchain@stable`
   - `Swatinem/rust-cache@v2`
   - `cargo doc --no-deps --document-private-items`

Add a top-level `concurrency:` group keyed by the workflow + ref so duplicate pushes cancel.

Document the CI architecture in `.github/workflows/README.md` (1 paragraph): "Three jobs: `test` runs the full suite on Windows and Ubuntu under both default and validation-enabled features; `clippy` enforces no warnings under `--all-features`; `doc` enforces the public API is documented. Validation layers are installed via `apt` on Ubuntu; on Windows, the Mesa software Vulkan ICD is used. The Vulkan golden tests from plan 05-01 run in the `test` job."

**Verify:** push to a feature branch; the workflow runs and all three jobs pass. (Local verification: `cargo test --lib --tests --features validation-layers` succeeds before pushing.)

**Files:** `.github/workflows/ci.yml` (new); `.github/workflows/README.md` (new, 1 paragraph).

**Depends on:** Task 2 (the feature must compile first).
**Parallel:** no.

## Task 4: Suppress (or fix) any validation errors surfaced by the test suite

**Action:**

After Task 3 runs the validation-enabled suite, the workflow will either pass (good) or fail with one or more wgpu validation errors. If it fails, this task is the remediation:

- Read each error message. The likely categories are:
  - **Buffer alignment**: a uniform buffer or vertex buffer is misaligned. Fix the buffer layout in the relevant renderer file.
  - **Push constant size**: a push constant block exceeds the wgpu limit. Reduce the block size.
  - **Bind group mismatch**: a `BindGroup` descriptor's layout does not match the shader's `wgsl` declaration. Fix one to match the other.
- Apply the smallest possible fix for each error. Do not add `#[ignore]` annotations to suppress the errors; that defeats the purpose.
- Re-run `cargo test --lib --tests --features validation-layers` until it passes.

If a validation error is unavoidable due to a wgpu 29 bug (rare), document it in a `// KNOWN-VALIDATION-ISSUE(wgpu#NNNN)` comment at the site and add a `#[ignore]` with a `// TODO` pointing to the upstream issue.

**Verify:** `cargo test --lib --tests --features validation-layers` passes cleanly with zero validation errors.

**Files:** whatever renderer files contain the fixed call sites; `// KNOWN-VALIDATION-ISSUE` comments if applicable.

**Depends on:** Task 3 (only runs if validation surfaces errors).
**Parallel:** no.

<notes>

**Why a Cargo feature, not a runtime env var:** env vars are easy to forget when running tests; cargo features are part of the build invocation and visible in CI logs. Env vars also complicate reproducibility — two runs with different env vars produce different behavior. The Cargo feature is the wgpu-ecosystem convention (see the `wgpu` examples repo).

**Why not `macos-latest`:** the GitHub-hosted free `macos-latest` runner does not expose a Metal device that wgpu 29 can drive headlessly. The `macos-14` or larger GitHub-hosted runners may work, but they are not in the free tier. The CI matrix is `windows-latest + ubuntu-latest` for the stress work; a future phase can add `macos-14` if needed.

**Why `cargo test --features vulkan-goldens` in the same workflow:** the visual golden tests from plan 05-01 only run under the `vulkan-goldens` feature. Putting the feature invocation in the same CI job (rather than a separate job) keeps the workflow small and the feedback loop tight.

**Risk:** Task 4 (suppress validation errors) may surface real bugs in the renderer that have been silently allowed. This is the intent of the phase — REND-03 is "Vulkan validation layers enabled in CI surface zero new buffer-alignment issues." The "zero new" wording acknowledges that the existing code may have latent issues that the validation layer catches; the plan's job is to fix them.
