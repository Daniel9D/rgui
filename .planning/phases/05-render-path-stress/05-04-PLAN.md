# 05-04: Frame budget micro-benchmark test (50-widget UI < 8ms CPU)

**Phase:** 5 (Render Path Stress)
**Plan:** 4 of 4
**Date:** 2026-06-04
**Source context:** `.planning/phases/05-render-path-stress/05-CONTEXT.md`, `.planning/phases/05-render-path-stress/05-RESEARCH.md`
**Decisions covered:** (Claude's Discretion — frame budget harness. Chose a deterministic `Instant::now()` wall-clock measurement inside an integration test over a `criterion` benchmark because: (1) `criterion` requires a `benches/` directory and either nightly or a special `#[bench]` attribute that the project does not currently use; (2) integration tests are already wired into the existing CI matrix; (3) the budget is a hard < 8ms ceiling, not a statistical regression detection, so the simpler approach matches the contract.)

<objective>

Populate `PerformanceMetrics.frame_time_ms` correctly (currently zeroed at `src/runtime/runtime.rs:1250`) and add a `tests/frame_budget.rs` integration test that builds a 50-widget desktop UI, measures the wall-clock CPU time of `UiRuntime::update(FrameInput)` over 100 iterations, and asserts the mean is under 8ms. After this plan, the project has a regression test that catches frame-budget regressions in the paint / event-dispatch path. REND-04 is satisfied.

</objective>

<context>

The `PerformanceMetrics` struct is defined at `src/core/snapshot.rs:171-205` with a `frame_time_ms: f32` field that is **defined but not populated**. The runtime constructs `PerformanceMetrics` at `src/runtime/runtime.rs:1242-1251` using `..PerformanceMetrics::default()` syntax, which zeros the `frame_time_ms` field. This is a Phase 4 deviation captured in `STATE.md` (item 3: "atlas field type change broke `render_wgpu_render_items.rs`; atlas_mut() restored" — this is a similar measurement-path gap, not the same bug).

The 60 fps target implies a 16.67ms frame budget. The CPU portion is typically half (8ms) on a modern laptop with a 2020+ integrated GPU. The project's performance constraint (PROJECT.md) says: "60 fps for typical desktop UIs on integrated GPUs. Each frame's full pipeline (layout + paint + render) must fit in ~8ms of CPU budget on a modern laptop."

A 50-widget UI is the project's canonical "typical desktop UI" — the 50 widgets are a representative mix of buttons, inputs, labels, boxes, lists, sliders, checkboxes, and progress bars.

The `FrameInput` and `FrameOutput` types are reached via `rgui::FrameInput` and `rgui::FrameOutput`. `UiRuntime::update(&mut self, input: FrameInput) -> FrameOutput` is the public seam. The output includes `output.debug_snapshot().performance.frame_time_ms` (which is what this plan populates).

</context>

## Task 1: Populate `frame_time_ms` in `UiRuntime::update`

**Action:**

In `src/runtime/runtime.rs`, find the `update` method (the entry point at the top of the method, around `runtime.rs:1218`). At the entry, capture `let frame_start = std::time::Instant::now();`. At the exit (just before constructing `PerformanceMetrics` at `runtime.rs:1242`), compute `let frame_time_ms = frame_start.elapsed().as_secs_f32() * 1000.0;` and pass it into the struct construction:

```rust
performance: PerformanceMetrics {
    frame_time_ms,
    ..PerformanceMetrics::default()
},
```

This replaces the current `..PerformanceMetrics::default()` zeroing pattern. The `frame_time_ms` field is the wall-clock duration of the entire `update` call (event dispatch + layout + paint + display-list assembly; does NOT include the wgpu render pass, which is owned by the host and called separately via `WgpuRenderer::render(&output)`).

Document in a comment: "frame_time_ms measures the CPU-side cost of `update`: event dispatch + layout + paint + display-list assembly. The wgpu submit + present cost is not measured here; that is a host-side concern and is profiled separately via `PerformanceMetrics.frame_time_ms` on the host's render path."

**Verify:** `cargo build --lib` succeeds; `cargo test --lib` passes (no regressions). Add a one-line unit test in `src/core/snapshot.rs`'s `#[cfg(test)] mod tests`: `frame_time_ms_field_is_populated_by_runtime` that constructs a `UiRuntime::default()`, calls `update(FrameInput::default())`, and asserts `output.debug_snapshot().performance.frame_time_ms > 0.0` (sanity check that the field is now populated, not zeroed).

**Files:** `src/runtime/runtime.rs` (add `Instant::now()` capture + elapsed at end); `src/core/snapshot.rs` (add the unit test).

**Depends on:** none.

## Task 3: Add `tests/frame_budget.rs`

**Action:**

Create `tests/frame_budget.rs` with the following tests:

1. **`frame_budget_50_widget_ui_under_8ms`** — calls `UiRuntime::default()`, builds the 50-widget UI via the helper from Task 2, then runs 100 iterations of `update(FrameInput::default())`. Computes:
   - `mean_frame_time_ms` = sum of `output.debug_snapshot().performance.frame_time_ms` / 100
   - `max_frame_time_ms` = max single iteration
   - Asserts `mean_frame_time_ms < 8.0`
   - Asserts `max_frame_time_ms < 16.0` (one-frame spike budget; 60fps = 16.67ms)

2. **`frame_budget_first_frame_is_warmup_excluded`** — same setup, but discards the first 5 iterations (warmup; first call often allocates caches) and asserts `mean_frame_time_ms` of iterations 5..100 is < 8.0.

3. **`frame_budget_50_widget_ui_throughput`** — measures total wall-clock time for 1000 iterations of `update(FrameInput::default())` and asserts the per-frame mean is < 8.0. This is a heavier version of test 1 that gives the JIT / CPU caches more chance to stabilize; if test 1 fails but test 3 passes, the budget is being met on average but the first 100 iterations have a cold-start cost.

Document the 8ms budget as a hard ceiling per `PROJECT.md`'s performance constraint. The tests must run in `--release` mode for meaningful measurements; gate them with `#[cfg(not(debug_assertions))]` and document in the file header: "Run with `cargo test --release --test frame_budget`. The 8ms / 16ms budgets are not meaningful in debug builds (debug builds are typically 10× slower)."

The release-mode gating is important: a debug-mode `cargo test` will fail the 8ms budget and the failure is not actionable. The CI workflow (plan 05-03) adds `cargo test --release --test frame_budget` as a separate CI step.

**Verify:** `cargo test --release --test frame_budget` passes all three tests on a modern laptop. `cargo test --test frame_budget` (debug) compiles but is skipped by the `#[cfg(not(debug_assertions))]` gate.

**Files:** `tests/frame_budget.rs` (new).

**Depends on:** Tasks 1 and 2.

<notes>

**Why `Instant::now()` and not a perf-event-based profiler:** the budget is a wall-clock measurement, not a microarchitectural profile. `Instant::now()` is monotonic and gives microsecond precision on every modern OS. A perf-event-based profiler (perf / Instruments / VTune) is the right tool for diagnosing *why* a frame is slow, not for asserting the budget is met.

**Why release mode for the test:** debug builds disable optimizations and add bounds checks, debug assertions, and `format!` strings throughout the paint path. The 8ms budget is meaningless in debug because a debug `update` typically takes 30-80ms. The `#[cfg(not(debug_assertions))]` gate is the standard Rust pattern for "this test only makes sense in release."

**Why 50 widgets and not 100 or 1000:** the project's `PROJECT.md` says "60 fps for typical desktop UIs on integrated GPUs" and the success criteria say "50-widget desktop UI's frame CPU budget is < 8ms." 50 is the canonical number in the spec; 100 would be testing a heavier UI than the spec asks for.

**Relationship to 05-01, 05-02, 05-03:** the frame budget test runs in CI independently of the visual goldens (05-01), the stress scene (05-02), and the validation layers (05-03). The four plans collectively cover REND-01, REND-02, REND-03, REND-04.

**Phase 4 deviation note (from STATE.md):** this plan fixes the third Phase 4 deviation ("PerformanceMetrics.frame_time_ms is a stub; ..PerformanceMetrics::default() zeros it at runtime.rs:1250"). The fix is the `Instant::now()` capture at the entry of `update`.
