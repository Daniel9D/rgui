# 05-02: Stress-test scene (headless 10k-row windowed list, bounded command count)

**Phase:** 5 (Render Path Stress)
**Plan:** 2 of 4
**Date:** 2026-06-04
**Source context:** `.planning/phases/05-render-path-stress/05-CONTEXT.md`
**Decisions covered:** D-01 (headless test, not winit example), D-02 (10k-row `list()` in `scroll_area()`), D-03 (scroll_area has fixed viewport height), D-04 (bounded command count assertion), D-05 (`// TODO(phase-7): drag` and `// TODO(phase-8): windowed list` annotations)

<objective>

Add a headless integration test that builds a 10,000-row list inside a fixed-viewport scroll area, renders it through the existing wgpu headless seam, and proves the produced `DisplayList` is bounded (under 2,000 commands total) and that the wgpu device surfaces zero validation errors. After this plan, the project has `tests/stress_scene.rs` exercising the worst-case `list` + `scroll_area` paint path and asserting the renderer's culling / view-binding optimization keeps the command count linear in viewport-visible rows, not linear in total rows. REND-02 is satisfied.

</objective>

<context>

The `list()` widget builder (re-exported from `rgui::widgets::list`) renders an N-row virtual list. The `scroll_area()` builder wraps a child in a fixed viewport that clips paint to the visible region. The combination should mean a 10k-row list inside a fixed-height scroll area produces a paint command count proportional to the visible row count (typically < 100), not to 10,000.

The `DisplayList` API exposes `output.display_list.commands().len()` for the raw command count and `output.stats.command_count` for the post-lowering count. The relevant existing tests are `tests/visual_goldens.rs` (8 single-screen scenes) and `tests/render_wgpu_render_items.rs` (17 unit-level render tests). There is no existing large-N render test.

The `WgpuRenderer` exposes `push_error_scope()` and `pop_error_scope()` (wgpu 29) which can capture validation errors emitted by the device during a render pass. The stress test must wrap the entire render in an error scope and assert the scope returns zero validation errors.

D-01 keeps the test headless (no winit). D-04 bounds command count at < 2,000. D-05 marks two seams with `// TODO` annotations for future phases (drag in phase 7, windowed list in phase 8).

</context>

<tasks>

## Task 1: Add the headless stress test

**Action:**

Create `tests/stress_scene.rs`. The test should:

1. Construct a `UiRuntime::default()` (single-window path is fine; multi-window is not the point of this test).
2. Build the element tree:
   ```rust
   scroll_area()
       .viewport_height(600.0)
       .child(
           list()
               .rows(10_000)
               .row_height(24.0)
               .item(|i| label(format!("Row {}", i))),
       )
   ```
   The exact builder names will need to be confirmed against `src/widgets/list.rs` and `src/widgets/scroll_area.rs` (or wherever the builders live — the public API is `rgui::widgets::list::list()` and `rgui::widgets::scroll_area::scroll_area()`). If the public API is different, use whatever the correct names are; the test's intent is the same.
3. Submit the tree via `runtime.update(FrameInput::default())` and capture the `FrameOutput`.
4. Wrap the render pass in `renderer.push_error_scope()` and `renderer.pop_error_scope()`; assert the returned `Option<wgpu::Error>` is `None`.
5. Assert `output.stats.command_count < 2_000`.
6. Assert `output.display_list.commands().len() < 2_000` (this is the raw count, which should be ≤ stats count).
7. If the command count exceeds 2,000, the test fails with a clear message naming the actual count and the expected bound.

Mark the file header with the two `// TODO` annotations:
- `// TODO(phase-7): drag` — near the `list` builder call, marking the future drag-and-drop seam.
- `// TODO(phase-8): windowed list` — near the `scroll_area` builder call, marking the future per-window scrollable list optimization.

Add a second, smaller test in the same file: `ten_row_list_is_at_most_10x_baseline` that builds a 10-row list, captures the command count as `baseline`, then asserts a 1,000-row list's command count is `< 10 * baseline` (linear scaling check; a 1,000-row list inside a 600px / 24px = 25-row viewport should produce the same command count as a 10-row list, but allow a 10× margin for any first-pass inefficiency).

**Verify:** `cargo test --test stress_scene` passes. If the existing renderer's `list` or `scroll_area` is not culling (i.e. the 10k-row list produces 10,000+ commands), this test will fail and the implementation gap must be fixed in this plan (see Task 2).

**Files:** `tests/stress_scene.rs` (new).

**Depends on:** none.
**Parallel:** yes (independent of Tasks 2 and 3).

## Task 2: Investigate culling gap if Task 1 fails (fallback)

**Action:**

If `cargo test --test stress_scene` fails because the command count is not bounded, inspect `src/widgets/list.rs` (or the relevant file) and `src/widgets/scroll_area.rs` to determine where the unbounded paint is emitted. The likely fix is one of:
- The list builder emits a paint command per row (10,000 commands). Add a viewport-visibility check in the list's paint path.
- The scroll_area does not clip its child to the viewport. Add a `ClipPush` / `ClipPop` pair around the child's paint.
- The list emits bounds-rect paints per row for hit-testing only; collapse them into a single per-viewport paint.

If a fix is needed, implement the smallest possible change that bounds the command count and re-run the test. Document the fix in a comment at the top of `tests/stress_scene.rs` explaining what the underlying issue was and where it was fixed.

**Verify:** `cargo test --test stress_scene` passes after the fix.

**Files:** `src/widgets/list.rs` (or wherever the list paint lives); `src/widgets/scroll_area.rs` (or wherever the scroll_area paint lives); `tests/stress_scene.rs` (add comment documenting the fix).

**Depends on:** Task 1 (only runs if Task 1 fails).
**Parallel:** no.

<notes>

**Why headless, not an `examples/` file:** D-01 explicitly chose a `tests/stress_scene.rs` integration test over an `examples/stress_scene.rs` winit example. The reason is CI feedback: an example requires a display server, GPU window, and event loop to exercise; an integration test runs in the same headless seam as the existing 8 visual goldens, with the same `RGUI_UPDATE_GOLDENS` workflow. The plan's name in `ROADMAP.md` says "examples/" but CONTEXT.md D-01 overrode that to `tests/`.

**Why < 2,000 commands, not < 100:** the bound is intentionally generous. A 600px / 24px viewport shows ~25 rows. The render path may also emit per-widget chrome (scrollbar, background, padding) which adds ~10 commands. 25 + 10 = 35 commands is the ideal. 2,000 is a 50× safety margin that gives the test slack to pass even if the first implementation of the culling is conservative (e.g. culls to 1,000 rows per pass). A future phase can tighten the bound to ~100 once culling is proven.

**Why `// TODO` annotations, not actual gaps in the test:** the test does not skip; the annotations mark where future phases will extend the stress scene to add drag interaction (phase 7) and windowed-list viewport binding (phase 8). The annotations are documentation, not `#[ignore]`.

**Relationship to 05-01 and 05-03:** the stress test runs in CI as part of the standard `cargo test` invocation, independent of the `--features vulkan-goldens` and `--features validation-layers` features.
