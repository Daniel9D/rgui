<objective>

Add a runnable doctest to every public type in the `rgui` crate root's `pub use widgets::spec::{...}` re-export list (30+ types). Fix the two pre-existing rustdoc broken-link warnings (`new_headless_for_tests` in `src/render/wgpu/mod.rs:165`, `UiTree` in `src/runtime/paint.rs:3`). After this plan, API-01 (every public type has a doctest) and API-02 (`cargo doc` builds without warnings) are satisfied.

</objective>

<context>

The `rgui` crate root (`src/lib.rs`) explicitly re-exports 30+ widget spec types via `pub use widgets::spec::{...}`. These are the documented "crate root public API" surface. Most of these types currently have `///` rustdoc comments but no runnable doctest. The standard Rust convention is to add a `///` rustdoc + ` ```rust ` block (no `no_run`/`ignore` unless the example has side effects) that compiles and runs as part of `cargo test --doc`.

The two pre-existing rustdoc broken-link warnings are documented in the Phase 5 verification report (`05-VERIFICATION.md`). Both fixes are 1-2 line changes; the link-resolving is straightforward (escape the brackets, or rename the symbol, or add a `use` import).

The `cargo doc --document-private-items` build must emit zero warnings (API-02 success criterion). The CI workflow (plan 05-03) runs this command on every push, so a `cargo doc` regression fails the build immediately.

D-01..04 (from `06-CONTEXT.md`): the user selected only the unwrap policy area. The doctest scope and format are Claude's Discretion: standard Rust convention (full usage examples for builder types, one-line smoke tests for opaque types like `Color` and `Point`).

</context>

## Task 1: Audit the crate-root public types

**Action:**

Read `src/lib.rs` and identify the full list of types in the `pub use widgets::spec::{...}` re-export block. For each type, decide whether it's:
- A **builder type** (e.g., `Element`, `list`, `scroll_area`) — gets a full usage example.
- A **spec type** (e.g., `ListSpec`, `SliderSpec`) — gets a construction example with `..Default::default()`.
- An **opaque type** (e.g., `Color`, `Point`, `Size`) — gets a one-line smoke test (`let _ = Type::default();`).
- A **variant type** (e.g., `AlertVariant`, `BadgeVariant`, `AvatarSize`, `ImageFit`) — gets an enum example showing the variants.

Build a mapping table:
- Type name → file location → doctest format (smoke / usage / variant).

The mapping table is the contract for Tasks 2-3. Write it to `src/lib.rs` as a `// DOCTEST AUDIT (Phase 6 06-01):` block immediately above the `pub use widgets::spec::{...}` block. Each line is `//   - {TypeName}: {doctest format} at {file:line}`.

**Verify:** The audit table is committed and the file builds clean.

**Files:** `src/lib.rs` (add audit table comment block).

**Depends on:** none.
**Parallel:** yes (Task 1 is read-only documentation work; Tasks 2-3 are per-file edits that depend on the audit).

## Task 2: Add doctests to the 30+ widget spec types in `src/widgets/spec.rs`

**Action:**

For each spec type in `pub use widgets::spec::{...}` (the audit table from Task 1 lists them), add a runnable `///` doctest to the type's `pub struct {TypeName}` definition. The doctest format depends on the type (per Task 1's mapping):
- Spec types (e.g., `ListSpec`, `SliderSpec`): `/// let _ = {TypeName}::default();` — proves the type + Default::default() resolve.
- Variant types (e.g., `AlertVariant`): `/// let _ = {TypeName}::Default;` (or whichever variant is the default).

The `///` doc comment is added immediately above the `pub struct {TypeName}` (or `pub enum {TypeName}`) line. The doctest must compile under `cargo test --doc` and run without panic.

**Special cases:**
- `SelectOption` (not in the original re-export list — verify by re-reading `src/lib.rs`) — add a doctest showing `SelectOption::new("value", "label")`.
- `WidgetSpec` — the umbrella enum that wraps all spec types. Doctest: `/// let _ = WidgetSpec::List(ListSpec::default());` (or similar) to show the enum variants.
- `ImageFit`, `AvatarSize`, `AlertVariant`, `BadgeVariant` — show 2-3 variants in the doctest, not all.

**Verify:** `cargo test --doc --features default` runs all new doctests and they pass. No regressions in the existing doctest suite.

**Files:** `src/widgets/spec.rs` (add doctests to 30+ struct/enum definitions). May also need to touch `src/widgets/forms.rs` or `src/widgets/feedback.rs` for the `input()`, `checkbox()`, `slider()`, `progress_bar()` builder types if they're in the audit table.

**Depends on:** Task 1.
**Parallel:** no (sequential within the spec.rs file; multiple commits if the spec.rs is large).

## Task 5: Add a regression test that asserts `cargo doc --document-private-items` exits 0

**Action:**

Create `tests/doc_build_clean.rs` with a single test `cargo_doc_build_emits_no_warnings` that:
1. Invokes `cargo doc --no-deps --document-private-items` as a subprocess (via `std::process::Command`).
2. Captures stdout and stderr.
3. Asserts the exit code is 0.
4. Asserts stderr does not contain "warning:" (case-insensitive substring match, allowing for future-proofing of "WARNING" or "Warnings" variants).
5. Asserts stdout does not contain "warning:" either (cargo emits warnings to stderr by default but some toolchains write to stdout).

The test is gated with `#[cfg(not(target_os = "windows"))]` if the subprocess invocation is platform-specific (Windows requires different shell handling). Verify by running on Windows; if it works, drop the gate.

The test runs in <10 seconds. It is the regression test for the API-02 success criterion.

**Verify:** `cargo test --test doc_build_clean` passes. The test fails if a future PR introduces a new rustdoc warning.

**Files:** `tests/doc_build_clean.rs` (new test file).

**Depends on:** Tasks 1-4 (the test should pass when run against a clean doc build, which only happens after all warnings are fixed).

**Parallel:** no (must run after the warnings are fixed to pass).

<notes>

**Why doctests are on the 30+ explicit re-exports, not the 190+ hidden re-exports.** The `#[doc(hidden)]` attribute on `pub use core::*;` is intentional (per bug-fix 8.5). The hidden re-exports are an implementation detail; the documented public surface is the explicit re-exports. API-01 says "every public type in the `rgui` crate root" — the hidden re-exports are explicitly NOT documented as part of the public surface.

**Why `cargo test --doc` runs in <30s, not minutes.** Doctests are compiled as a single test binary (`--doc` flag compiles them all together). The 30+ doctests are tiny (one-liner smoke tests + small usage examples). Total compilation + execution time is dominated by the lib compilation, not the doctest count.

**Why a separate `tests/doc_build_clean.rs` instead of a lib test.** The lib test runs in-process; the `cargo doc` invocation requires a subprocess. The subprocess is the only way to test the doc build's exit code. A lib test can't observe the doc build's stderr.

**Why a regression test for `cargo doc` at all.** Phase 5's CI workflow runs `cargo doc --no-deps --document-private-items` as a separate job with `RUSTFLAGS=-D warnings`. Any future PR that introduces a new rustdoc warning fails the CI build. The `tests/doc_build_clean.rs` test is a local equivalent — catches the regression at `cargo test` time, before pushing.

**Why not test for the existence of a doctest on every type.** A test like "every type has a `///` rustdoc" is brittle (the rustdoc could be empty, or one-line, or a paragraph). The actual API-01 success criterion is "every public type in the `rgui` crate root has a doctest" — the test is `cargo test --doc --features default` succeeds. If a type has no doctest, the test fails (rustdoc emits a warning for a public type without docs, which fails `cargo doc`).

**Why the audit table in `src/lib.rs` (Task 1).** A grep-able list of "which types need doctests and where" makes the work auditable. The table is a 30-line comment block; it doesn't bloat the lib.rs and gives a future reviewer a quick reference for "what's covered by 06-01".

**Relationship to 06-02 / 06-03:** 06-01 is independent of 06-02 (different files) and 06-03 (different files; the painter guide is in `docs/`, not `src/`). All three plans can run in Wave 1 in parallel, or sequentially in the order 06-02 -> 06-01 -> 06-03 (smallest first for fast feedback).

</notes>
