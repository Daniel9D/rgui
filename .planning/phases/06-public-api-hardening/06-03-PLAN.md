**Action:**

```
# Writing a Custom Widget

## Why custom widgets?

The `rgui` library ships a fixed set of widget kinds (button, input, list, etc.).
Sometimes you need a widget that isn't in the built-in set — e.g., a colored
status pill, a custom progress dial, a domain-specific chart. The
`WidgetPainter` extension point lets you add a new widget kind to the
runtime without modifying `rgui` itself.

## The `WidgetPainter` trait

The `WidgetPainter` trait is the per-widget paint dispatch. It has two methods:

- `background_color(&self, ctx: &PaintCtx<'_>) -> Color` — the widget's background
- `paint_content(&self, ctx: &mut PaintCtx<'_>, cmds: &mut Vec<PaintedCommand>)` — the widget's content

The trait is `Send + Sync` (it can be shared across threads in the paint pipeline).

## Step 1: define your `WidgetPainter`

\`\`\`rust
use rgui::core::{Color, Rect, Size, Point};
use rgui::runtime::paint::{PaintCtx, PaintedCommand};
use rgui::runtime::WidgetKind;
use rgui::widgets::Element;
use rgui::widgets::spec::WidgetSpec;

pub struct StatusPillPainter;

impl rgui::runtime::WidgetPainter for StatusPillPainter {
    fn background_color(&self, _ctx: &PaintCtx<'_>) -> Color {
        Color::rgb(0, 128, 0)  // green
    }

    fn paint_content(&self, ctx: &mut PaintCtx<'_>, cmds: &mut Vec<PaintedCommand>) {
        // Emit a single rect command for the pill's body
        cmds.push(ctx.draw_rect(ctx.rect, Color::rgb(0, 200, 0), 8.0, 0));
    }
}
\`\`\`

## Step 2: register your painter

Add a new `WidgetKind` variant and register the painter at app startup:

\`\`\`rust
use std::sync::Arc;
use rgui::runtime::{register_widget_painter, WidgetKind};

let my_kind = WidgetKind::Button;  // reuse an existing kind, or add a custom one
register_widget_painter(my_kind, Arc::new(StatusPillPainter));
\`\`\`

## Step 3: use your painter in an `Element`

The painter is invoked whenever the runtime paints a widget of the registered
`WidgetKind`. If you reused an existing `WidgetKind::Button`, the existing
`button()` builder now paints with your `StatusPillPainter`:

\`\`\`rust
let _element = rgui::widgets::button("OK");
\`\`\`

## Step 4: unregister on shutdown

\`\`\`rust
use rgui::runtime::unregister_widget_painter;
unregister_widget_painter(my_kind);
\`\`\`

## Step 5: integration-test your painter

The runtime's existing test infrastructure (`tests/visual_goldens.rs`) tests
the built-in painters. For a custom painter, add a similar test:

\`\`\`rust
#[test]
fn custom_status_pill_renders() {
    let mut runtime = rgui::runtime::UiRuntime::default();
    let _ = runtime.update(rgui::runtime::FrameInput {
        root: rgui::widgets::button("OK"),
        viewport: rgui::Size::new(400.0, 200.0),
        ..Default::default()
    });
    // ... [assertions on the display_list] ...
}
\`\`\`

## When to write a custom widget

- You need a widget that the built-in set doesn't provide.
- The custom widget is a paint-only change (no new event dispatch, no new layout).
- The custom widget can be expressed in terms of the existing `Element` + `WidgetSpec` machinery.

## When NOT to write a custom widget

- You need a new event type (e.g., a new keyboard shortcut, a new pointer gesture). Add a new `UiEvent` variant instead.
- You need a new layout primitive (e.g., a `ZStack`). Add a new `PrimitiveKind` instead.
- You need a new accessibility role. Add a new `Role` instead.
```

The guide is rendered as a markdown file. The code blocks are illustrative; they may not compile against the current `rgui` API without verification. The example in Task 3 is the runnable verification.

## Task 3: Add `examples/custom_widget.rs` — a runnable example that registers a custom painter

**Action:**

Create `examples/custom_widget.rs` that demonstrates the full custom-widget flow:

```rust
//! Phase 6 / Plan 06-03: writing a custom widget.
//!
//! Demonstrates the `WidgetPainter` extension point. Defines a
//! `StatusPillPainter` that paints a green pill background, registers
//! it for `WidgetKind::Button`, builds a `button("OK")` element, runs
//! `UiRuntime::update`, and asserts the painter was invoked.
//!
//! Run with: `cargo run --example custom_widget`

use std::sync::Arc;
use rgui::runtime::{
    register_widget_painter, unregister_widget_painter, FrameInput, UiRuntime, WidgetKind,
    WidgetPainter, PaintCtx, PaintedCommand,
};
use rgui::core::Color;
use rgui::widgets::button;
use rgui::Size;

pub struct StatusPillPainter;

impl WidgetPainter for StatusPillPainter {
    fn background_color(&self, _ctx: &PaintCtx<'_>) -> Color {
        Color::rgb(0, 128, 0)
    }

    fn paint_content(&self, ctx: &mut PaintCtx<'_>, cmds: &mut Vec<PaintedCommand>) {
        cmds.push(ctx.draw_rect(ctx.rect, Color::rgb(0, 200, 0), 8.0, 0));
    }
}

fn main() {
    // Register the custom painter for the Button kind
    register_widget_painter(WidgetKind::Button, Arc::new(StatusPillPainter));

    // Build a button element — when painted, the runtime will invoke
    // StatusPillPainter instead of the default Button painter.
    let root = button("OK");

    // Render
    let mut runtime = UiRuntime::default();
    let output = runtime.update(FrameInput {
        root,
        viewport: Size::new(400.0, 200.0),
        ..Default::default()
    });

    println!("Rendered {} paint commands with custom StatusPillPainter",
             output.display_list.commands().len());

    // Unregister on shutdown
    unregister_widget_painter(WidgetKind::Button);
}
```

The example is gated with `required-features` in `Cargo.toml`'s `[[example]]` table (similar to the `rml_showcase` example). The example requires no special features (the `register_widget_painter` / `unregister_widget_painter` functions are in the default features).

Add an entry to `Cargo.toml`:

```toml
[[example]]
name = "custom_widget"
```

(If the example requires any features for compile, add `required-features = [...]`.)

<notes>

**Why the example is in `examples/`, not in the guide itself.** The guide is markdown; the example is runnable Rust. Keeping them separate means the guide can be rendered (e.g., on docs.rs) without compiling, and the example can be tested independently.

**Why a `TestPainter` with an atomic counter.** The `paint_content` method doesn't return a value (it mutates a `&mut Vec<PaintedCommand>`). To assert the painter was invoked, the painter needs side effects. An atomic counter is the simplest side effect that is `Send + Sync` and can be shared between the painter and the test.

**Why the example reuses `WidgetKind::Button`.** The built-in `WidgetKind` enum is `#[non_exhaustive]`, so adding a custom variant from outside the `rgui` crate requires a public API for adding variants. The example reuses an existing variant to demonstrate the registration / unregistration flow without that additional API. The guide notes this as a limitation and a possible future enhancement.

**Why the guide is in `docs/`, not `.planning/`.** The `.planning/` directory is for GSD workflow artifacts (PROJECT.md, ROADMAP.md, STATE.md, phase CONTEXTs, etc.). The `docs/` directory is for user-facing documentation. The guide is user-facing.

**Why the guide is markdown, not rustdoc.** The guide is a multi-page narrative (5 sections, ~120 lines). rustdoc is per-symbol and doesn't have a place for a "writing a custom widget" guide. A `docs/` markdown file is the right convention.

**Relationship to 06-01 / 06-02:** 06-03 is independent of 06-01 (different files) and 06-02 (different files). All three plans can run in Wave 1 in parallel, or sequentially in any order.

</notes>
