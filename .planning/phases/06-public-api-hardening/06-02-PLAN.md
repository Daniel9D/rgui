<notes>

**Why 1 unwrap, not more.** The Phase 6 unwrap audit (per `06-RESEARCH.md`) found 1 production-code `.unwrap()` in `src/runtime/`. The 2 `.unwrap()` calls in `src/runtime/state.rs` are in `#[cfg(test)]` blocks (test fixtures) and are excluded per D-01. The 5 `.expect("widget painter registry poisoned")` calls in `src/runtime/paint.rs` are already in good shape.

**Why the test excludes `#[cfg(test)]` blocks.** Test code's `.unwrap()` calls are idiomatic (e.g., `assert_eq!(result.unwrap(), expected)` after a `Result.is_ok()` check). Excluding them keeps the test focused on production code per D-01. The regex strips the test modules before searching for `.unwrap()`.

**Why `#![deny(clippy::unwrap_used)]` at the module level, not the crate level.** The crate level would also flag `.unwrap()` in `tests/`, `examples/`, and `benches/`. The runtime is the highest-stakes area (the paint path runs on every frame); examples and benchmarks can use `.unwrap()` freely.

**Why the expect message names the matches! check.** The `matches!(kind, Some(WidgetKind::Input | Textarea))` check is the invariant: when it returns true, `kind` is `Some(Input)` or `Some(Textarea)`. The expect message names this so a future test failure ("WidgetKind is Some(WidgetKind::Input | Textarea) when matches! ... is true") points directly at the violated invariant. This is the standard Rust idiom.

**Why no CI changes.** The CI workflow (plan 05-03) already runs `cargo clippy --all-targets --all-features -- -D warnings` with `RUSTFLAGS=-D warnings`. The new `#![deny(clippy::unwrap_used)]` is automatically honored on every push. No CI changes needed.

**Why the 50-widget frame-budget test is in the verification list.** The unwrap replacement is at `src/runtime/runtime.rs:632` (text-hit geometry for `Input`/`Textarea` widgets). The 50-widget frame-budget test (plan 05-04) doesn't include `Input` or `Textarea` widgets, so the unwrap replacement doesn't affect the 8ms budget. Including the frame-budget test in the verification is a safety net: it confirms the unwrap replacement is on a cold path, not the hot path.

**Relationship to 06-01 / 06-03:** 06-02 is independent of 06-01 (different files) and 06-03 (different files). All three plans can run in Wave 1 in parallel, or sequentially in any order. 06-02 is the smallest plan (1 line change + 1 attribute + 1 test file); running it first gives fast feedback on the unwrap audit before tackling the larger doctest work in 06-01.

</notes>
